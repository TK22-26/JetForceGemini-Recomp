# Playtesting and reporting

Play normally and report problems that help us improve the game. You do not
need to run developer tests, submit successful checklists, or make a pull request.

## A few things to try

As you play, check that you can reach gameplay, move, jump, aim, shoot, and
return from the pause menu. Watch for obvious graphics or audio problems.
After a normal save opportunity, quit and relaunch to check your progress.
These are suggestions, not a required test session or completion report.

Crashes, freezes, progression blockers, broken controls, incorrect graphics or
audio, and save/load failures are all worth reporting.

## Check whether the problem is already known

Read [known issues](known-issues.md) and search
[existing issues](https://github.com/TK22-26/JetForceGemini-Recomp/issues).
Add to a matching issue when you have useful new information, such as clearer
reproduction steps, a requested hardware comparison, or a failure after a fix.
Keep repeated occurrences of the same problem in that issue.

## Create a report

1. In the launcher, click **Create support report** after the problem. Do this
   before starting another setup or game session: the current exporter selects
   the latest session. After a launcher crash, reopen it and create the report
   before launching again.
2. Open the [playtest issue form](https://github.com/TK22-26/JetForceGemini-Recomp/issues/new?template=playtest.yml),
   or reply to a matching issue, and attach the ZIP.
3. Describe where you were, what you did, what you expected, what happened,
   and whether it repeats. Include whether you started a new game or loaded
   existing progress, plus keyboard/controller details.

Use one issue per distinct problem. If several failures are part of the same
setup attempt or reproduction sequence, describe that sequence together.
If a report cannot be created, submit the issue anyway and explain that.
Source-build reports should include the game-source commit from `git rev-parse HEAD`.
The source field in the ZIP identifies the launcher build; it does not identify
a separately selected game's source revision.

For setup failures, include the short error shown by the launcher, removing
personal file paths. The ZIP can identify the failed stage without retaining
the detailed installer error. For a freeze, create the report while the launcher
is still responsive, before another session replaces it as the newest report.

## What the current support ZIP contains

The launcher exports filtered `launcher.log` and `native.log` files with
version information, setup/launch stages, error codes, and a runtime hash when
available. Some native failures also record an exception code, failure
category, or fault offset. This helps identify builds and recurring failures;
your reproduction steps are still essential.

It does not contain a stack trace, crash dump, hang snapshot, recent gameplay
recording, or GPU/driver details. Include your GPU/driver and input device in
the issue form. Nothing uploads automatically.

Attach the ZIP generated by the launcher. Keep ROMs, game assets, saves,
generated game builds, and raw setup logs out of issue attachments.
Use [security reporting](../SECURITY.md) for security-sensitive problems.

## After reporting

Keep the affected local build until the issue is understood. A maintainer may
ask for a specific reproduction step or a retest on a named newer build.
Reply in the same issue with whether that change fixed the problem.
